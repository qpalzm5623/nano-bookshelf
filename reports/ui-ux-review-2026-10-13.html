NANO BOOKSHELF · PRODUCT EXPERIENCE REVIEW

나노의 책장
UI/UX 및 실사용 개선 보고서

작성일 2026년 10월 13일 · 검토 방식: 로컬 소스 정적 분석 · 대상: 학생 / 학원 원장·교사 / 본사 운영자

현재 제품의 가장 큰 개선 과제는 “사용자가 완료했다고 믿는 일”과 “실제로 저장·전달된 일”을 일치시키는 것입니다.

브랜드 색상, 학생 캐릭터, 역할별 포털, 도서 배정부터 첨삭·학부모 리포트까지 이어지는 기능 구성은 좋은 출발점입니다. 다만 현재 프리뷰 경로에는 고정 학생 정보, 학원 간 대체 데이터, 모의 완료 처리, 저장 계약 불일치가 남아 있습니다. 이 상태에서는 화면을 더 예쁘게 다듬어도 실제 운영 신뢰를 확보하기 어렵습니다.

권장 순서: ① 본인·소속 및 제출/발송 상태 정확성 → ② 학습·배정·첨삭 흐름과 복구 → ③ 검색·표·모바일 사용성 → ④ 시각 정돈·성능·동기부여.
실사용 파일럿의 범위는 아래 P0 항목이 해결된 핵심 흐름으로 한정하는 것이 합리적입니다.
검토 범위강점실사용 시나리오우선순위상세 개선점화면 개선안실행 순서검증 계획근거 목록

1. 검토 범위와 판단의 한계

현재 시작 경로를 우선 검토했습니다. public_html/index.html의 로그인은 본사·학원·학생 프리뷰 파일로 이동하며, 루트 start_server.bat도 본사 프리뷰를 열도록 되어 있습니다. 따라서 최신 프리뷰 세 화면과 연결 JavaScript를 이번 보고서의 주 분석 대상으로 삼았습니다.

구분검토한 자료판단 범위
현재 프리뷰index.html, student_preview.html, admin_preview.html / .js, master_preview.html / .js메뉴, 화면 구성, 상태 표시, 저장·조회 흐름, 주요 이벤트 처리
연결·배포 구조vercel.json, package.json, service-worker.js, api 파일 목록, lib/api-example.ts프리뷰와 서버 연동의 경계, 캐싱, 존재하는 로컬 경로
기존 PHP 화면application/controllers/Home.php, controllers/Book.php, views/book/quiz.php, views/admin/include/left.php 일부기존 화면과의 구조 차이를 확인하는 보조 표본

기존 PHP에는 세션 기반 로그인·역할별 메뉴·퀴즈 AJAX 처리가 존재합니다. Prisma CRUD 예제도 있습니다. 그러나 이 사실만으로 프리뷰가 그 기능에 연결되었다고 판단하지 않았습니다. 프리뷰에서 확인한 결함을 기존 PHP 전체 또는 실제 운영 서비스 전체의 결함으로 일반화하지 않습니다.

확인한 것: 코드의 조건·저장 키·완료 처리·CSS 수치, 주요 JavaScript 구문 검사.
추론한 것: 해당 로직이 사용자에게 줄 혼란과 예상 불편.
추가 확인할 것: 실제 렌더링, 화면 겹침, 실제 통신 응답, 운영 DB 상태, 체감 속도, 터치·키보드·스크린리더 사용성. 브라우저 테스트·스크린샷·실사용 인터뷰는 수행하지 않았습니다. 이하 크기·시간 수치는 개선 목표 또는 파일 크기이며 실측 사용자 성과가 아닙니다.

3. 실제 사용자가 겪을 경험

다음 내용은 코드에서 도출한 예상 경험입니다. 실제 사용자의 발언이나 인터뷰 결과를 뜻하지 않습니다.

사용자와 목적현재 예상되는 경험제품이 제공해야 할 경험
학생 · 수업 전 배정 책의 퀴즈 풀기홈에서 캐릭터·배너·최근/인기/권장 도서를 먼저 보고 과제를 찾음. 답안 작성 중 나가면 이어하기가 불명확하며 제출이 교사 화면으로 연결되지 않을 수 있음.홈 첫 영역에서 내 과제 확인 → 이어하기/시작 → 답안 검토 → 서버 접수 확인 → 교사 확인 대기
교사 · 제출 답안 첨삭하기회원 관리에서 시작해 학습 관리로 이동. 학생 제출 기록을 찾지 못하거나 다른 학원 대체 기록을 볼 가능성. 첨부 파일은 이름만 저장될 수 있음.담당 반의 미첨삭 목록으로 시작 → 실제 학생 답안 → 첨삭 저장 → 첨부 확인 → 학부모에게 보낼 내용 미리보기
원장 · 학부모에게 리포트 전달“발송 완료”를 보고 전달되었다고 믿지만 프리뷰 함수는 로컬 이력만 변경. 이후 학부모가 수신하지 않았다고 하면 원인 확인이 어려움.수신자·내용·동의 확인 → 발송 접수 → 제공업체 결과 조회 → 실패 이유와 재시도
본사 · 특정 학원/회원 문제 처리많은 컬럼을 가로 탐색하고, 검색어가 자동완성 방어 로직에 의해 지워질 수 있음. 일부 KPI는 고정 기간·고정 숫자를 표시.주의 대상 우선 조회 → 필터 유지 → 상세 처리 → 목록 위치로 복귀 → 집계 기준과 갱신 시각 확인
학부모 · 자녀의 변화 이해리포트·포트폴리오 표본에는 긍정적인 정성 문구가 있으나 실제 답안·장르·일정 근거보다 넓은 평가를 제공할 가능성.이번 기간의 사실, 답안 사례, 교사의 관찰, 다음 학습 제안을 구분해 읽을 수 있음

핵심 여정은 다음과 같이 한 번의 학습 기록을 중심으로 이어져야 합니다.

교사가 도서 배정→학생이 내 과제 확인→퀴즈·생각 담기 제출→교사가 첨삭→학부모 리포트 전달

모든 단계가 academyId / studentId / bookId / assignmentId / attemptId 같은 일관된 식별자로 연결되어야 합니다. 화면의 이름이나 고정 문자열만으로 연결하면 동명이인·학원 전환·재응시 상황을 처리하기 어렵습니다.

5. 상세 개선점과 완료 기준

P0 · 01로그인한 사람과 화면의 소속을 일치시키기

확인: 학원 정보는 저장된 선택 학원 또는 대표 학원에서 초기화되고, 세션에 학원명이 있을 때 일부 값만 덮어씁니다. 해당 학원 학생이 없으면 다른 학원 학생 최대 30명을 반환하고, 학습 기록도 다른 학원 기록 최대 25건을 대체 표시합니다. 프리뷰에서는 운영 화면 진입 시 역할을 강제 확인하는 흐름을 찾지 못했습니다.

예상 영향: 신규·빈 학원의 원장이 “우리 원생”으로 오인하고 조회·수정할 수 있습니다. 소속이 없는 로그인에서도 대표 학원 화면이 나오면 시스템을 신뢰하기 어렵습니다.

개선: 세션의 사용자·역할·학원 ID를 화면의 기준으로 사용합니다. 운영 모드에서는 대표 학원/타 학원 데이터로 대체하지 말고 “소속 학원 확인 필요” 또는 실제 빈 목록을 표시합니다. 교사는 담당 반, 원장은 소속 학원, 본사는 허용된 전체 범위를 서버에서도 검증합니다. 데모 학원 전환은 데모 모드에서만 명시적으로 제공합니다.

완료 기준: 소속·담당 반이 다른 계정과 원생 0명인 학원으로 각각 접속해 타 학원 학생·기록이 표시되지 않아야 합니다. 로그아웃 후 세션을 폐기하고 보호 화면 재진입 시 재인증해야 합니다.

근거: admin_preview.js:298, 412, 484, 2719 / index.html:574, 685, 755 / student_preview.html:9295.
기존 PHP의 세션 기반 권한 구조는 별도이며, 이 지적은 프리뷰 경로에 해당합니다.

P0 · 02학생의 제출 기록을 교사가 읽을 수 있게 연결하기

확인: 학생 제출 함수는 학생명·반명을 고정 문자열로 기록하고 NANO_LEARNING_LOGS에 저장합니다. 학원 화면은 NANO_LEARNING_LOGS_<학원ID>를 읽으며 구버전 정리 시 일반 키를 삭제합니다. 학생 기록에는 안정적인 studentId / academyId 연결도 없습니다.

학생 제출: NANO_LEARNING_LOGS
학원 조회: NANO_LEARNING_LOGS_ + academyId
학원 초기 정리: localStorage.removeItem('NANO_LEARNING_LOGS')

예상 영향: “선생님께 제출되었습니다”라고 믿은 학생의 답안을 교사가 찾지 못합니다. 다른 학생이 풀어도 고정된 학생의 기록처럼 만들어질 수 있습니다.

개선: 사용자 세션에서 식별자를 얻고 동일한 제출 API·저장 스키마를 사용합니다. 서버가 반환한 attemptId와 접수 시각을 결과 화면에 표시하고, 교사는 그 기록을 조회합니다. 제출 접수와 첨삭 완료는 분리합니다.

완료 기준: 학생 A·B가 각자 다른 기기에서 제출하면 교사 화면에 정확한 학생·학원·도서·답안으로 나타나야 합니다. 새로고침·재로그인 후에도 유지되고 반복 클릭은 같은 제출을 중복 생성하지 않아야 합니다.

근거: student_preview.html:7302, 7412, 7420 / admin_preview.js:2719, 2756

P0 · 03실제 작업 결과에 맞춰 완료 문구 표시하기

확인: 학생 비밀번호 변경은 두 입력값 비교 후 성공 토스트만 표시합니다. 학원 리포트 카톡 발송은 로컬 발송 기록과 SUCCESS 상태를 추가합니다. 본사 비밀번호 발급·회원 엑셀 다운로드·템플릿 다운로드·연결 확인·백업 등에도 토스트만 표시하는 함수가 있습니다. 본사 회원 엑셀 업로드는 파일 내용을 파싱하지 않고 샘플 회원 2명을 추가합니다.
